## 0. 结论摘要（先看这段）

**A. 状态总线** —— 建议做，但要**收窄范围**，理由在 §2.1：

| 需求原文 | 实测结论 | 建议 |
|---|---|---|
| 禁止裸调 `fs.writeFileSync` 读写"共享账本" | **没有真正的共享账本**：51 个写点里，每个文件都只被**一个**组件写（各写各的）；真正跨组件的是**读**（4 处组件读别人的 state） | 不做"统一账本"，做**统一 IO 原语**：读缓存 + 写合并 + 按 key 排队 + 原子落盘 |
| 每 N 秒防抖落盘 | 目前 21 处已手写 tmp+rename（写法各异），另有 5 处 `appendFileSync` **完全不原子** | 统一走 StateStore，`append` 也变成"读-改-写" |
| 收拢 `setInterval` | 11 处 + 2 处递归 `setTimeout` | 中央 Heartbeat，**错峰**（错开 0-60s）避免同帧撞车 |
| 全局发送限流 | 目前限流散在 silence-ping / 各工具的 gate 里 | 中央 RateLimiter，按 `chatKey` + 全局两级 |

**B. 前缀缓存** —— 宿主**已经**做了一大半（931 行 `cache-warm.js` + `deferVolatile` 机制），真正的缺口只有一个：

> **`travel-whale` 的 6 个 promptSections（函数体 9,209 字符）里含动态内容，且 `volatile: false` —— 它们进 system，system 每轮变，前缀缓存全废。**

这一条修掉，命中率能上一个台阶；数值量化（元气/好感档位）是第二层优化。**两者都在组件侧可解，不需要改宿主源码。**

按当前数据估算命中天花板 ≈ **88%**，目标 80% 可达；**前提是先把 system 抖动按住**。

## 2. 方案 A：StateStore（统一状态原语）

### 2.1 范围界定（先说不做什么）

| 不做 | 为什么 |
|---|---|
| ❌ 把 12 个组件的账本搬到一个"大 JSON" | 现在没有共享写冲突；合并只会把故障半径放大到全组件 |
| ❌ 引入 sqlite / leveldb | 数据量小（最大 27KB/文件），进程内跑，.NET+Node 双读不现实 |
| ❌ 跨进程文件锁 | 宿主单进程；多开靠 data 目录隔离。跨进程锁会把简单问题做成分布式问题 |
| ❌ 改数据格式/迁移历史存档 | 违反既有硬约束「存档不搬家」（见 `00-先读我.md`） |

**做**：统一 IO 原语 + 读缓存 + 写合并 + 按 key 排队 + 原子落盘 + 崩溃自愈。

### 2.2 落地位置

`courtyard-bus` 现有一条明确的红线：**零 fs / 零网络 / 纯内存**（它自己注释里写的）。
**不要破坏这条红线** —— StateStore 作为**兄弟 provider** 挂在同一插件下：

```
plugins/courtyard-bus/
  index.js            ← 现有 pub/sub，零 fs，不动
  store.js            ← 新增：StateStore
  clock.js            ← 新增：Heartbeat
  limiter.js          ← 新增：RateLimiter
  plugin.json         ← capabilities += courtyard.store / courtyard.clock / courtyard.limit
```

消费方式（与 bus 一致，谁需要谁拿）：

```js
const store = api.capability('courtyard.store');       // 拿不到 = 降级到本地 fs（必须兼容）
```

### 2.3 API 设计

```js
// —— 读：走内存缓存，命中不发 IO ——
const doc = await store.read(key);                    // key = 'sleep-mood/mood-chain'
const doc2 = store.peek(key);                         // 同步读缓存（有则返回，无则 undefined）
await store.warm(['courtyard-map/snapshot', 'qzone/state']);  // 启动时预热

// —— 写：按 key 排队 + 防抖合并 ——
await store.update(key, (prev) => next, { merge: 'replace' });  // 原子更新（fn 必须是纯函数）
await store.append(key, line);                                  // 追加行（jsonl），内部转读-改-写
await store.flush(key);                                         // 强制立刻落盘（关键操作：发消息前）
await store.flushAll();                                         // 退场/热重载前

// —— 观察 ——
store.watch(key, (doc) => {});                        // 变更通知（内部走 bus.publish）
store.stats();                                        // { hits, misses, writes, coalesced, pendingKeys }
```

**关键选择：`update(key, fn)` 而不是 `write(key, obj)`。**
理由：并发两个 `write` 会互相覆盖；`update` 在锁内基于最新值计算，天然解决"读-改-写"竞态（现在 51 处手写里，至少 learning-loop 的 ledger 与 sleep-mood 的 mood-chain 有这种风险）。

### 2.4 一致性模型

| 维度 | 设计 |
|---|---|
| 锁粒度 | **按文件 key**，不是全局。`Map<key, Promise>` 串行队列；同 key 排队，不同 key 并发 |
| 防抖 | 默认 `debounceMs = 3000`（可配）；期间同 key 的多次 `update` 只落盘**一次**（合并后） |
| 原子性 | `write(tmp) → fsync → rename(tmp, target)`；tmp 名带 pid+随机后缀，避免两个实例撞名 |
| 崩溃安全 | 启动时扫描 `*.tmp` 残留 → 删除（rename 是原子的，残留 tmp 一定是废弃的） |
| 读缓存 | 进程内 `Map<key, {doc, mtime, loadedAt}>`；写入后**立即**更新缓存（写穿），读永远读缓存 |
| 外部改动 | 每 `recheckMs = 60_000` 比对 `mtime`（只 stat，不读），变了才重读 —— 应对"用户手改文件" |
| 上限 | 单文件 > 2MB 或条目 > 5000 时告警并降级为直读（不缓存），避免内存膨胀 |

### 2.5 与现有代码的兼容

```js
// 组件侧改造示例（learning-loop）
- fs.writeFileSync(tmp, JSON.stringify(st, null, 1), 'utf8');
- fs.renameSync(tmp, STATE);
+ await store.update('learning-loop/state', () => st);
```
**降级路径必须保留**：拿不到 `courtyard.store` 时走原来的直读直写。这是硬要求（组件可能被单独安装）。

### 2.6 迁移清单（12 组件 / 18 文件 / 51 写点）

| 期 | 组件 | 写点 | 风险 | 收益 |
|---|---|---:|---|---|
| P1 | learning-loop（7） | `appendFileSync` 不原子，最该先改 | 低 | 消灭 4 处不原子追加 |
| P1 | sleep-mood（3 文件） | 每轮被读多次（元气/心境） | 低 | 读缓存收益最大 |
| P2 | qzone（diary/social，5） | 已有 tmp+rename，主要换统一锁 | 中 | 去重 2 处手写 |
| P2 | silence-ping（3） | 有 `STORE.broken` 自愈逻辑，要保留 | 中 | 统一 |
| P3 | travel-whale（state.js 等 6 处） | **核心数据，动之前先全量备份** | **高** | 读缓存（courtyard-map 每轮读） |
| P3 | 其余（autobiography/life-system/mind-wish/knowledge-base） | 简单 | 低 | 收口 |

**每期独立可回滚**：StateStore 与直读直写并存，按组件逐个切，`components.json` 里加开关。

## 3. 方案 A2：中央 Heartbeat

### 3.1 现状问题

11 处 `setInterval` 各起各的：`bili-whale/scheduler.js` 3 个、travel-whale `ticker` 1 个、autobiography/main 1 个、sleep-mood 1 个……
后果：① 同一秒内多个定时器同时触发 → CPU 峰值 + 多个 IO 同时落盘；② 没人统一管"夜里要不要降频"；③ 每个组件自己写 `unref/clear`，热重载漏清就泄漏。

### 3.2 API

```js
const clock = api.capability('courtyard.clock');
const off = clock.every('travel-whale/tick', 60_000, async () => { ... }, {
  jitter: 0.15,        // ±15% 抖动，天然错峰
  runOnStart: false,   // 注册时是否立刻跑一次
  priority: 'normal'   // high = 不被降频
});
clock.at('hourly-digest', '0 * * * *', fn);   // 简易 cron（5 字段）
clock.pauseIfIdle(true);                     // 空闲 10 分钟自动降频到 5 倍间隔
```

**实现要点**：单 `setInterval(1000)` 主循环 + 到期队列（最小堆），所有任务串行 await，单任务超时 30s 后跳过并记录。

### 3.3 错峰规则

按 `key` 哈希把首次触发时间摊到 `[0, period)` 内 → 避免"整点齐发"。实测现在 `ticker` 60s、`scheduler` 3 个、`autobiography` 都在启动时立刻开始，**启动后前 5 秒是 IO 尖峰**。

## 4. 方案 A3：全局发送限流（RateLimiter）

### 4.1 为什么需要

现在各组件自己判断"要不要说话"（silence-ping 的主动私信、travel-whale 的明信片、qzone 的主动评论），**没有全局视角**：极端情况下同一分钟她可能在 3 个群各发一条 + 私聊 1 条 + 空间 1 条。

### 4.2 设计

```js
const rl = api.capability('courtyard.limit');
const ok = rl.take('send', { chatKey, weight: 1 });   // 同步、无 IO
if (!ok.allowed) return { skip: true, reason: ok.reason };
```

令牌桶，三维：

| 维度 | 默认 | 说明 |
|---|---|---|
| 全局 | 30 条 / 10 分钟 | 所有会话合计 |
| 单会话 | 8 条 / 10 分钟 | 同一 `chatKey` |
| 主动消息（非回复） | 3 条 / 小时 / 会话 | 回应用户不占这个桶 |

> ⚠️ **只做"发不发"的建议，不接管发送**。真正发送仍走 `send_message`（本地补丁有去重/分条/CQ 转义）。限流器**拒绝时必须有降级**：记日志 + 静默跳过，绝不报错打断会话。

## 5. 方案 B：缓存友好提示词

### 5.1 宿主已有什么（别重复造）

`src/cache-warm.js`（931 行）已经在做：

| 能力 | 说明 |
|---|---|
| 形状指纹 | `shapeKeyOfSystem()` + `shapeFingerprint()`，按 system+tools 的"形状"分桶 |
| 落盘前缀 | `data/cache-warm-prefix.json`（现役 14,855 字符 system + 93 工具名） |
| 真实调用前预热 | `warmBeforeRealCall()`，同形状去重、10 分钟桶 TTL、429 冷却 |
| 形状变化响应 | `noteShapeChange()` / `noteContextTier()` / `markCurrentShapeWarmed()` |
| volatile 分离 | `deferVolatile` + `isVolatileSection()` → 易变 section 挪到 **user 末尾** |

⇒ **"静态前置、动态后置"这条原则，宿主本身已经实现了**（`prompt.js:361-370` 注释写得很清楚）。
我们缺的是**让我们的组件配合它**。

### 5.2 三个动作（按收益排序）

#### B-1（最高收益，零补丁）把动态 section 标成 volatile

```js
// components/skills/travel-whale/index.js —— promptSections()
- { id: 'travel-whale-away', title: '…', content: awayText }
+ { id: 'travel-whale-away', title: '…', content: awayText, volatile: true }
```

需要标的（逐个确认内容是否真每轮变）：

| section | 是否动态 | 处理 |
|---|---|---|
| `travel-whale-away` | ✅ 在途中/在家切换 | `volatile: true` |
| `travel-whale-adopt` | ⚠️ 待确认（邀请提示会不会每轮刷） | 确认后标 |
| `travel-whale-reborn` | ⚠️ 待确认（重生/换人设时变） | 若只在事件后变 → 不标（保持 system，靠 cache-warm 的形状分桶兜） |
| `travel-whale-borrowed-voice` | ⚠️ 待确认（借嘴说话期间才有） | 同 adopt |
| `travel-whale-rule` / `home-lore` | ❌ 静态 | 保持 system |
| `life-system` `life-worldbook` | ⚠️ 待确认（3 处动态词） | 确认后决定 |

**预期收益**：system 从"每轮可能变"变成"只在静态配置变时变" → 前缀命中从"接近 0"回到"接近天花板"。
**风险**：低。这些 section 挪到 user 末尾后语义不变（宿主有 `renderSectionBlock` 统一格式）；唯一代价是它们不再受 system 的"最高优先级"影响。

#### B-2（中收益，纯组件侧）高频数值量化

现状：元气 0.1 的变化会改一次描述文本（sleep-mood）、好感每 1 点可能刷新（favor-core）。这些文本若在 system → 每轮 miss；若在 user 尾部 → 每轮 miss 但**只影响尾部**。

量化规格（建议值，可配）：

| 量 | 范围 | 档位 | 文本更新条件 | 档位词示例 |
|---|---|---|---|---|
| 元气 `vitality` | 0-100 | **10 档** | 跨档才更新 | 0-9 虚脱 / 10-29 疲惫 / 30-49 蔫 / 50-69 平常 / 70-84 有精神 / 85-100 满电 |
| 好感 `favor` | -100~100 | **5 档** | 跨档才更新 | 疏远 / 普通 / 熟 / 亲 / 很亲 |
| 情绪 `mood` | 枚举 | 原值 | 只在**切换**时更新 | 保持现有 tag 体系 |
| 待办/念想 | 计数 | 粗粒度 | 数量级变化才更新（0 / 1-2 / 3+） | — |

实现建议：在**产出文本的地方**做档位映射（`tierOf(vitality)`），而不是在 prompt 层做 diff。
**副作用**：她对自己的状态感知变粗（50 和 59 感觉一样）。这是"省 token"的必然代价，**建议配一个"精确值仅在她主动查询时给"的旁路**（`mood_status` 工具已存在，天然满足）。

#### B-3（高收益，需打补丁）`【此刻状态】` 与 `【当前时间】` 的最终位置

宿主 `buildUserPrompt()` 现在的顺序（实测）：

```
【记忆】 → 【场景】 → 【过去状态】 → 【本次唤醒】 → 【此刻状态】 → 【活跃模式】 → 【余烬】 → 【当前时间】
                                              ↑ 每轮都变的数值在这里
```

问题：`【此刻状态】` 在**中段**，它一变，后面的 `【活跃模式】/【余烬】` 全部 miss。

两个选择：

| 方案 | 做法 | 收益 | 代价 |
|---|---|---|---|
| B-3a | 由**我们的组件**提供 volatile section 承载状态文本，宿主那段 `【此刻状态】` 关掉/留空 | 中（不用改宿主，若宿主有开关） | 需确认宿主那段是否可配置 |
| B-3b | **打核心补丁**：把 `【此刻状态】` 移到 `【当前时间】` 之前（即尾部） | 高（尾部漂移不再影响任何前文） | 核心补丁 +1 项，需回归 |

⇒ **先做 B-1/B-2，再看 B-3 要不要打补丁**。因为 B-1 做完，system 就稳了；`【此刻状态】` 只影响 user 内部，而 user 本来就在末尾。

### 5.3 验收指标（必须可量化）

**命中率定义**（按 token 加权，不是按次数）：

```
hitRate = Σ cachedTokens / Σ promptTokens        （来自每次响应的 usage.cached_tokens）
```

采集：宿主已经在 `orchestrator.js:1113` 累加 `cachedTokens`，只需**加一个落盘**（`data/cache-stats.jsonl`，每轮一行：`{at, chatKey, prompt, cached, toolsTokens, systemChars}`）。

对比方法：
1. 先加统计（1 天数据基线）
2. 做 B-1 → 观察 2 天
3. 做 B-2 → 观察 2 天
4. 目标：`hitRate ≥ 80%`（按 token 加权，按天汇总）

**附加指标**（防止"命中率高但体验差"）：
- 每轮 `promptTokens` 绝对值（应下降）
- 工具调用成功率、她"出戏/重复/茫然"的人工抽样（每周 20 条）

## 7. 风险表

| 风险 | 影响 | 缓解 |
|---|---|---|
| StateStore 丢写（防抖期间进程被杀） | 丢最近 N 秒的账 | 关键操作（发消息/结算）前显式 `flush()`；`debounceMs` 默认 3s，不超过 5s |
| 缓存读到旧值（外部改了文件） | 显示不一致 | 60s mtime 巡检 + 提供 `store.invalidate(key)` |
| volatile 标注标错（静态内容被挪到末尾） | 她"忘了规则" | 一次只标 1-2 个 section，观察 2 天；`rule`/`home-lore` 不标 |
| 数值量化导致观感变粗 | 她觉得"她不够细腻" | 保留 `mood_status` 精确查询旁路；档位词可配 |
| Heartbeat 单点故障 | 全部定时任务停 | 单任务 try/catch + 超时；主循环自检（连续 3 次空转 → 重启） |
| RateLimiter 误拦 | 该说话时沉默 | 只拦"主动消息"，回复不占桶；拒绝时记日志便于复盘 |
| 改 travel-whale state 引发数据损坏 | 存档坏 | P5 单独一期，改前全量备份 + 影子写（双写对比 1 天） |
