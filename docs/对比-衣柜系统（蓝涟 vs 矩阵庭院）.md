# 对比：「蓝涟·衣柜（全年龄公开版）」 vs 矩阵庭院的衣柜

> 2026-10-28 ｜ 拆包对象：`蓝涟·衣柜（全年龄公开版）.zip`（4 文件 / 32 KB）
> 结论先说：**它是"外观状态系统"，我们是"旅行纪念品 + 经济解锁"的玩法系统**。它解决"换角色"，我们解决"值得买"。
> 用户提的问题（角色热插拔了、衣柜还锁人）**成立，而且根因比"少了功能"更具体**：我们有两套名册。
>
> **★ 2026-10-28 追加（用户拍板，本文件第三节的"who 绑人"已作废）**：
> 服装**改绑世界/地区**，任何角色都能自由更换任何服装。实现方式：
> · `outfitsFor()` 不再按 `who` 过滤，直接返回全部 60 套（解锁仍按 `region|area`）
> · `who` 降级为**「原型/出处」**，只在衣柜页当一列展示（表头从「谁穿」改成「原型」）
> · `worn[girlId]` 保留（每人各自穿着），存档零迁移
> · 已删掉 `whale_wear` 里"这套是给谁的"那道闸与相应文案
> 见 `travel-whale 4.7.0`。

## 一、它是什么（拆包结果）

```
lanlian-wardrobe/
├─ plugin.json          1.7 KB   独立插件，enabledByDefault: false
├─ index.js            16.1 KB   数据读写 → 识别 → 注入 → 3 个工具 → 2 个钩子
├─ lib/wardrobe-core.js 9.3 KB   4 张数据表 + 纯函数（**换角色只改这里**）
└─ README.md            4.9 KB   架构说明（写得很清楚，值得学）
```

**三个工具**

| 工具 | 作用 |
|---|---|
| `wardrobe_list` | 看衣橱（按 daily / out / home / hair / headwear 分类） |
| `wardrobe_wear` | 换衣服 / 发型 / 头饰（名字模糊匹配，`findWardrobe` 打分：id 100 → name 90 → 90包含 70 → text 50 → tags 30） |
| `outfit_change` | 手记兜底（衣橱里没有的、脱到一半的） |

**两个钩子**

```
after-response        她从 send_message 里说出「换上XX」「把头发扎起来」→ detectOutfitChange() 自动认
before-llm-messages   每轮把【你现在的穿着】拼到末条 user 消息末尾（**只私聊**）
```

**数据**
- `wardrobe.json`（可选）：自定义衣橱，没有就用代码里的默认示例
- `state.json`：`sessions[chatKey].outfit = { text, tags, clothesText/Tags, hairStyle/Tags/Text, headwear*, style*, itemId, byTool, at }`

**四条核心设计**（README 自己列的）
1. **唯一真相源**：穿着只存 `state.json` 的 `outfit`，别的系统不许再存一份
2. **分层槽位**：衣服 / 发型 / 头饰 / 临时风格（"头发湿着"放 style 层，不污染衣服）
3. **唯一写入口** `applyOutfit()`：负责同时重算 `text`（给人看）和 `tags`（给生图），保证两者永远一致
4. **默认保守**：只私聊注入、自动识别只在明确匹配到物品时才动手、默认关闭

**换角色怎么办**：改 `lib/wardrobe-core.js` 的四张表（`DEFAULT_WARDROBE` / `SCENE_WARDROBE` / `HAIR_STYLES` / `HEADWEAR_STYLES`）。角色数据**不在代码里**，全在可替换的表 + 可选的 `wardrobe.json`。

## 二、我们的是什么

```
outfits.js            435 行 / 25.3 KB   服装表 + 名册 + 价格
whale_wear（工具）                        买下并换上一套（要"去过那个地方" + 2000 亿 TOKEN）
whale_wardrobe（工具）                    列出每位少女现在穿什么（文本返回）
courtyard-map 面板                        只有一张 KPI 卡「衣柜：已拥有 N 件 / 穿着 X」
```

存档形状（`chatState.wardrobe`）：

```js
{ owned: { 'miko': true, ... },          // 已买
  worn:  { fox: 'miko', ... } }          // 每位少女现在穿哪套；'default:<girlId>' = 回到她原本那身
```

服装条目长这样：

```js
{ id: 'mechanicus', name: '机械神教红袍', region: 'warhammer40k', area: '太阳系',
  who: 'whale', price: OUTFIT_PRICE, wear: '穿一身…（给生图的整段提示词）' }
```

- `region/area` = **解锁判据**（必须真去过那个子区域）
- `who` = **谁能穿**（一位少女一套，`outfitsOf(girlId)` 过滤）
- `wear` = 一整段描述（既给人看也喂生图，**没有独立 tags**）
- `price` = 经济消耗（2000 亿 TOKEN）

## 三、真正的差异（不是"缺功能"，是定位不同）

| 维度 | 蓝涟·衣柜 | 我们的衣柜 | 判断 |
|---|---|---|---|
| **定位** | 角色外观状态机（通用骨架） | 旅行纪念品 + 经济解锁（玩法） | 各有所长，**不该互相取代** |
| **解锁** | 无，衣橱里有的都能穿 | 去过对应 `area` 才能买 | 我们更"游戏"，是卖点 |
| **价格** | 无 | 2000 亿 TOKEN | 同上 |
| **槽位** | 衣服 / 发型 / 头饰 / **临时风格** | **只有整套** | **我们缺** |
| **展示 vs 生图** | `text` 与 `tags` **分开维护、由 `applyOutfit` 同步** | 一段 `wear` 混用 | **我们的隐患**：给人看的中文直接喂生图，改文案会动画面 |
| **写入口** | 唯一（`applyOutfit`） | 散在工具里 | 我们缺约束 |
| **换装方式** | 工具 + **自动识别**（after-response） | 只靠模型调工具 | 我们缺自动化 |
| **注入** | 每轮 → 末条 user 消息（**只私聊**） | 无注入（面板看，模型不知道） | **我们缺**：她不知道自己现在穿着什么 |
| **角色耦合** | 靠数据表替换（换角色=改表） | **`WARDROBE_GIRLS` 写死 8 个**、`who` 写死归属 | **我们有问题，见下** |
| **多角色** | 单角色（一份 state 一套 outfit） | 多少女、一人一套 | 我们更复杂 |
| **代码量** | 32 KB，零依赖 | 25 KB + 工具 + 面板 | 相当 |

## 四、你提的问题：衣柜"锁角色"的根因

我们的 `outfits.js` 注释自己写着：

> `id` 与 `state.js` 的 `COMPANIONS` 对齐；`whale` 是她本人。

但实际是**两套名册**：

| 名册 | 在哪 | 能不能换 |
|---|---|---|
| `COMPANIONS`（旅伴名册，人格/立绘/加成） | `state.js`，**可由 `persona/companions.json` 整体替换**（persona-pack 机制） | ✅ 热插拔 |
| `WARDROBE_GIRLS`（衣柜里能被穿的少女） | `outfits.js` **字面量写死 8 个** | ❌ 换角色不动它 |

后果很具体（不是"感觉不妥"）：

1. **换 persona 后新角色穿不了衣服** —— `WARDROBE_GIRLS` 里没有她，`outfitsOf()` 永远返回空；
   `whale_wear` 也会直接回「没有叫「X」的少女。可选：…（写死那 8 个）」（`tools-more.js:598-601`）
2. **旧角色的衣服留在存档里** —— `worn[girlId] = outfitId` 记的是 id，那位少女不在了，键还挂着
3. **面板 KPI 与旅伴页对不上** —— 「穿着」卡显示的还是老八位里的某一套
4. `whale`（小鲸鱼本人）是特例：她是主 persona，所以"看起来还能用" —— 一旦主 persona 换了，这套就直接空转

**所以这不是"该不该学蓝涟"，而是我们内部已经有两份真相源了。** 这是必须修的一致性问题，优先级与"要不要加槽位"完全不是一回事。

## 五、值得抄的四件事（按性价比排序）

| # | 借什么 | 为什么值得 | 改动量 |
|---|---|---|---|
| 1 | **名册单一真相源**：`WARDROBE_GIRLS` 改为从 `COMPANIONS` 派生（内置表降级为兜底） | 修掉"锁角色"，与 persona-pack 一致 | 小（1 处 + 面板 1 处） |
| 2 | **`text` / `tags` 拆开**：`wear`（中文展示）与 `tags`（英文生图）分离，由统一写入口重算 | 现在改一句中文会连带改画面；以后加发型也必须有这个 | 中（要补 tags 字段，可渐进：缺 tags 时回落 `wear`） |
| 3 | **每轮注入【现在的穿着】** | 现在她"不知道自己穿着什么"，换装后聊天/写信会自相矛盾 | 小（一个 hook，只在私聊/主群白名单） |
| 4 | **发型 / 头饰 / 临时风格三槽** | 表现力提升最直观；"头发还湿着"这类状态现在无处安放 | 中（数据结构 + 面板 + 1 个工具参数） |

**可以借鉴但不建议照搬的**：

- **`after-response` 自动识别换装**：他们用正则匹配 `换|穿|脱` + 物品名。我们是**群聊**场景，群里聊到"换衣服"（讨论剧情、别人换衣服）都会误触发；而且我们的服装是"花 2000 亿买的"，自动识别等于白拿。**建议只在私聊 + 已有该套时才允许自动切换**，或干脆不做。
- **默认关闭**：他们是通用骨架所以保守；我们的衣柜是主玩法，得默认开。

## 六、顺手发现的两个小问题（对方包里）

1. **`index.js:50` 写死了作者机器的绝对路径**：回退分支在 `QQ_AGENT_DATA_DIR` 缺失时，
   指向作者本机「用户目录 · AppData · QQ Agent · data」。正常情况走 `QQ_AGENT_DATA_DIR` 不会踩到，
   但**公开包里不该出现作者本机路径**（我们自己的脱敏闸就是拦这个，本文档第一版也因此被拦下）。
2. **全年龄版仍保留 `underwear` 条目**（`DEFAULT_WARDROBE` 最后一条「棉质内衣」）。与它 README 里"不做内衣分类"的说法略有出入 —— 不影响使用，只是口径不严。

## 七、我的建议（分两步，别混在一起）

**第一步（修 bug，必须先做）**
- `WARDROBE_GIRLS` 改为 `COMPANIONS` 派生 → 换 persona 后衣柜自动跟着换
- 面板衣柜页分组同步
- 存档里指向"已不存在的少女"的 outfit，读取时**忽略但保留**（不删用户数据）

**第二步（增强，可与第一步分开评审）**
- `text`/`tags` 拆开 + 统一写入口
- 每轮注入【现在的穿着】
- 发型/头饰/临时层

**不建议**：为了对齐而砍掉 `region/area` 解锁与 2000 亿价格 —— 那是我们的差异化，蓝涟那份是"骨架"，本来就没有玩法。

## 附：两份实现的接口对照（便于抄代码）

| 概念 | 蓝涟 | 我们 |
|---|---|---|
| 穿着状态 | `state.json` → `sessions[chatKey].outfit` | `chatState.wardrobe.worn[girlId] = outfitId`（`'default:<id>'` = 回本装） |
| 衣橱清单 | `wardrobe.json` → `items[]`（**可覆盖**，不用改代码） | `outfits.js` 的 `OUTFITS[]`（代码内，**不可覆盖**） |
| 谁能穿 | 无（一套大家都能穿） | `who: girlId`（一对一） |
| 名册来源 | 数据表内联（换角色改表） | `WARDROBE_GIRLS` **写死 8 个**，与 `COMPANIONS` 不同源 |
| 解锁 | 无 | `region/area` 去过才能买 |
| 展示文本 | `outfit.text` | `outfit.wear` |
| 生图 tags | `outfit.tags`（独立字段） | 无（直接拿 `wear`） |
| 写入口 | `applyOutfit()` 唯一 | 工具内直接改 `worn` |
| 自动识别 | `after-response` | 无 |
| 注入 | `before-llm-messages`（私聊） | 无 |
| 面板 | 无（纯后端） | 一张 KPI 卡 + `whale_wardrobe` 文本 |
